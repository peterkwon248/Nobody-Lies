## 0. 가장 먼저 — 이것부터 읽을 것

### 0.1 구현 전에 플레이테스트가 선행된다

**Claude Design 프로토타입(`추리게임.dc.html`)에 산장 사건이 통째로 구현되어 있다.** 프롤로그부터 결말까지, 조사 23개, 5장 19공란, 채점까지 동작한다.

따라서 순서는 이렇다.

```
1. 프로토타입 단일 파일 export
2. 플레이테스트 (9장 참조)
3. 설계 보정
4. 프로덕션 구현      ← Claude Code의 시작점
```

**이 게임은 아직 한 번도 플레이된 적이 없다.** 40개 넘는 설계 결정이 미검증이며, 특히 검증기가 예측한 "조사 5회"가 실측과 맞는지 모른다. 그 숫자가 틀리면 난이도 체계 전체가 다시 계산된다.

**검증되지 않은 설계를 프로덕션 스택으로 옮기면 두 번 만들게 된다.**

### 0.2 게임이 하지 않는 것 — 절대 규칙

이 게임의 상품은 **"내가 알아냈다"는 감각**이다. 아래를 위반하면 상품이 사라진다.

> **게임이 플레이어의 판단에 대해 하는 말은 최종 채점 하나뿐이다. 그 전까지 완전한 침묵.**

| 금지 | |
|---|---|
| 실시간 채점 | 장을 완성해도 정답 여부를 알리지 않는다 |
| 모순 경고 | "확보한 물증과 어긋납니다" 없음 |
| 게임이 하는 텍스트 강조 | 볼드 · 하이라이트 · 색칠 |
| 유용도 시각 구분 | 결정적 단서와 레드 헤링이 완전히 동일하게 생겨야 함 |
| 프로필의 유죄 판정 | 사실만 표시, `기회 있음 ✓` 금지 |
| 조사 추천 · 힌트 | 없음 |
| 자동 분석 기능 일체 | 모순 탐지 · 타임라인 해석 등 |

**이 규칙은 개발 중 일곱 차례 다른 형태로 재발했다.** 배너 → 진술 볼드 → 프로필 판정 → 분석 보조 토글 → 모순 경고 → 물증 카드의 `뜻` 필드 → 격자 자동 추출.

전부 "친절한 UI의 기본값"에서 나온다. 보통 앱은 중요한 것을 강조해주는 게 미덕이지만 이 게임은 그것이 정답 누설이다.

**새 기능을 만들 때마다 확인할 것: "이 화면이 플레이어가 내려야 할 결론을 미리 말하고 있는가?"**

### 0.3 한 번 보여주고 사라지는 텍스트는 버그다

이 게임은 교차 참조가 본질이므로 모든 텍스트는 재접근 가능해야 한다.

- 토스트는 "어디에 새 것이 생겼다"는 신호만. 내용은 해당 화면에 영구히
- 조사 결과 전문은 조사 기록에 보존. 요약본으로 대체 금지
- 장 완성으로 공개된 정보는 provenance 라벨과 함께 영구 표시
- 결말은 클리어 후 재접근 가능

### 0.4 런타임 LLM은 0이다

**예외 없다.** 런타임 LLM이 들어오면 "이 사건은 조사 3회로 풀린다"를 증명할 수 없게 되고, 난이도 산정 · UGC 워크샵 · 순위표가 전부 무너진다.

빌드 타임 LLM은 4곳만 — 진술 산문 / 프롤로그 / 번역 / UGC 누설 검사. 결과는 파일에 고정된다.

**유혹이 오지만 반드시 코드로 처리할 곳**: 모순 판정, UGC 진단, 난이도 산정.

## 1. 저장소 3분리 — 최우선 계약

```
Case               불변. 사건 정의
PlayerAnnotations  가변. 플레이어가 만든 것
CaseProgress       가변. 진행 기록
```

| | 성격 | 범위 | 비고 |
|---|---|---|---|
| `Case` | **불변** | 사건 하나 | 정적 파일. CDN 배포 가능 |
| `PlayerAnnotations` | 가변 | 사건 하나 | 하이라이트 · 메모 · 인용 · 셀 마킹 · 상황판 배치 |
| `CaseProgress` | 가변 | 전체 | 이어하기 · 클리어 여부 · 점수 |

**`Case`가 불변이라는 게 이 프로젝트의 인프라 전략 전체를 결정한다.** 사건 파일이 정적이므로 서버 없이 CDN에 올려두면 되고, 협동 모드 전까지 서버가 거의 필요 없다.

```ts
type PlayerAnnotations = {
  highlights: { textRef: string; range: [number, number]; kind: '표시'|'확인'|'의심'|'모순' }[]
  notes: { id: string; content: string; quote?: string; source?: '확정'|'주장'; target?: string }[]
  cellMarks: { person: string; slot: string; kind: '확인'|'의심'|'모순' }[]
  boardItems: { id: string; kind: 'person'|'evidence'|'note'; x: number; y: number; links: string[] }[]
}

type CaseProgress = {
  caseId: string
  status: 'unplayed' | 'in_progress' | 'cleared' | 'failed'
  actionsUsed: number
  reopensUsed: Record<number, boolean>   // 장별 재개봉 사용 여부
  elapsedMs: number
  clearedAt?: number
  savedState?: PlayerAnnotations
}
```

**협동 모드(v2) 대비**: 조사 결과에 `by: PlayerId`, `shared: boolean` 필드를 미리 넣어둔다. 나중에 추가하면 저장 구조를 뜯어야 한다.

## 2. 레이아웃과 로직을 분리한다

모바일은 반응형 축소가 아니라 **재설계**다. 이 게임의 핵심인 교차 참조(좌우 2단)가 모바일에서 성립하지 않기 때문이다.

```
공유    Case · 검증 · 채점 · 상태 관리 · 토큰
분기    레이아웃 · 내비게이션 · 일부 화면 구성
```

**지금 정하면 공짜고 나중에 고치면 비싸다.** 판정 로직이 화면 컴포넌트에 섞이면 걷어내는 것이 큰 작업이 된다.

모바일 설계는 플레이테스트 이후다. 다만 아래만 메모해둔다.

- 우측 디테일 패널 → 바텀 시트
- 좌측 사이드바 12항목 → 하단 탭 5그룹 + 더보기
- 격자 5열 → 가로 스크롤 또는 시간대 단일 표시

## 3. 사건 데이터 스키마

`deduction-engine/src/types.ts`가 정본이다. 핵심만 옮긴다.

```ts
type Case = {
  id, title
  scale: 'daily' | 'campaign'
  budget: number                    // 조사 예산
  incident: { kind: IncidentKind; subject: string; description: string }
  prose?: { source: 'authored'|'template'|'llm'; model?: string }
  people: Person[]
  victim, culprit: PersonId
  trick: { type, props, staging, flaw }
  evidence: Evidence[]
  facts: Fact[]
  actions: Action[]
  chapters: Chapter[]
  reveals: Reveal[]
  reopenPerChapter: number          // 장당 재개봉 허용 (현재 1)
}
```

### 3.1 진실의 원본은 `presence`다

```ts
type Person = {
  id, name, age, job
  gender: '남' | '여'
  hiddenRole: 'ringleader'|'accomplice'|'coerced'|'investigator'|'unaware'
  presence: { slot: SlotId; location: LocationId }[]
}
```

**무고한 사람의 진술 주장은 `presence`에서 도출된다.** 손으로 쓰지 않는다. 그것이 "무고한 사람은 거짓말하지 않는다"를 보장하는 유일한 방법이다.

### 3.2 공란 라벨은 고정 어휘

```
인물 · 장소 · 시각 · 도구 · 동기 · 정체 · 은폐수단 · 위장물
마지막목격자 · 접촉수단 · 은닉처 · 사인 · 물품 · 협박대상
```

어휘를 닫아두면 생성기가 돌고, 한국어 조사 처리를 한 번만 짜면 되고, **템플릿 20개 번역으로 사건 1000개가 번역된다.**

**`공범`은 어휘에서 폐기했다.** 라벨 존재 자체가 "범인 말고 한 명 더 있다"를 조사 0회에 누설하고(§0.2 절대 규칙), 유일성 검증이 인물 1명에서 인물 쌍으로 올라가며, "무고한 사람은 거짓말하지 않는다"의 이음매에 앉아 진술 도출 규칙을 하나 더 요구한다. **진실 세계의 `accomplice` 역할은 남는다** — 배경과 관계 그래프 간선으로만 존재하고 공란으로 묻지 않는다.

**단, 구성은 고정하지 않는다.** 모든 사건이 5장이고 4장이 항상 `감춰진 사건`이면 플레이어가 첫 화면에서 반전을 예측한다. UI가 5장을 전제하지 않도록 한다.

### 3.3 채점 부문은 라벨에서 도출

```ts
const DOMAIN_OF: Record<BlankLabel, '물증'|'정황'|'심증'> = {
  도구: '물증', 은폐수단: '물증', 위장물: '물증',
  물품: '물증', 은닉처: '물증', 사인: '물증', 접촉수단: '물증',
  인물: '정황', 장소: '정황', 시각: '정황', 마지막목격자: '정황',
  동기: '심증', 정체: '심증', 협박대상: '심증',
}
```

## 4. 판정 로직 — 검증기에서 이식할 것

`deduction-engine/src/verifier.ts`가 정본. 알고리즘이 전부 나와 있으므로 설계 부담은 없다.

### 4.1 런타임에 필요한 것

| 기능 | 내용 |
|---|---|
| `deriveFacts` | 획득 물증 + 완성 장 수 → 성립하는 fact 집합 |
| 장 완성 판정 | 공란 전부 채워짐 → 자동 완성 · 잠김 |
| 트리거 평가 | 장 완성 / 특정 조사 → 정보 공개 |
| 채점 | **최종 제출 시 1회.** 부문별 |

### 4.2 저작 시점에만 필요한 것 (앱에 안 넣어도 됨)

유일성 검증, 교착 검사, 최단·기대 경로, 조합 수 검사, decoy 검증, 확보 단어 획득 가능성. **UGC 에디터를 만들 때 필요하며 v1 플레이에는 불필요하다.**

### 4.3 채점

```
점수 = 사용한 조사 횟수 + 정확도 + 소요 시간
```

- 부문별 내역으로 표시. **100점 환산 금지** (19공란이 자연 척도)
- 지목 공란은 부문에 섞지 않고 통과/실패로 별도 표시
- 결과 화면에 각 심증 공란의 근거를 `Fact.revealedBy`에서 렌더링 (입력받지 않음)

## 5. 장 · 공란 · 정보 공개

### 5.1 장은 순차 잠금

- 1장만 열려 있고, 완성하면 2장이 열린다
- **잠긴 장은 번호만 남기고 전부 가린다** — 제목 · 공란 라벨 · 후보 유형 · 개수
- 라벨이 곧 사건 구조이기 때문. `물품·정체·협박대상`만 봐도 숨은 범죄의 존재가 드러난다

**장 순서는 의존성 순서와 일치해야 한다.** 앞 장이 뒤 장보다 먼저 풀릴 수 있어야 하며, 검증기가 이를 강제한다.

### 5.2 장 완성과 재개봉

```
공란 전부 채움 → 자동 완성 · 잠김 → (재개봉 1회 가능)
```

- `장 확인` 버튼 없음. 자동 완성
- **정답 여부와 무관하게 완성되고 다음 장이 열린다**
- 재개봉은 장당 1회. 이미 공개된 정보는 회수하지 않는다 (진행 보장)
- **최종 제출만이 완전 확정**

완성된 장은 자동으로 접힌다. 접힘은 표시 상태이며 언제든 펼칠 수 있다.

### 5.3 정보 공개 트리거

```ts
type RevealTrigger =
  | { on: 'chapterComplete'; chapterOrder: number }
  | { on: 'action'; actionId: string }
```

**공란 단위 트리거는 쓰지 않는다.** 잠금과 충돌한다.

장을 완성했는데 아무 정보도 안 열릴 수 있다. 매번 보상이 나오면 리듬이 기계적이 된다. **다만 다음 장이 열리는 것은 항상 발생해야 한다.**

### 5.4 공개 정보의 유용도

공개 정보는 전부 **확정 층**이므로 거짓일 수 없다. 함정은 "거짓"이 아니라 **"참이지만 무관한 것"**이다.

| yield | 뜻 |
|---|---|
| `path` | 필수 경로를 엶 |
| `narrow` | 탐색 축소 |
| **`decoy`** | **참이지만 정답과 무관** |
| `flavor` | 서사만 |

```
난이도 ∝ decoy 비율 × 조사 예산의 빡빡함
```

**decoy 없이도 풀려야 한다.** 검증기가 "decoy는 fact를 제공하지 않는다"를 강제한다.

**decoy와 path를 시각적으로 구분하지 않는다.**

## 6. 정보 층위 — 화면 전체에 적용

| 층 | 성격 | 출처 | 시각 |
|---|---|---|---|
| **확정** | 반박 불가 | 브리핑 · 확보 물증 | 실선 · 채움 |
| **주장** | 미확정 | 진술 5개 | 따옴표 · 인물색 |
| **판단** | 채점 전 미확정 | 보고서 공란 | 입력 필드 |

**모순 판정은 확정 층만 기준으로 한다.** 진술끼리 안 맞는 것은 모순이 아니라 "누군가 거짓말 중"이다.

**모순 경고를 제거했으므로 확정과 주장의 대조를 플레이어가 전부 혼자 해야 하고, 그 대조가 일어나는 자리가 메모다.** 인용 카드의 층위 라벨은 필수 기능이다.

같은 원리가 관계 그래프와 상황판에도 적용된다.

| | 저자 | 시각 |
|---|---|---|
| 관계 그래프 | **게임** (조사로 확보한 관계) | 실선 |
| 상황판 | **플레이어** (가설) | 점선 등 |

## 7. 조사

### 7.1 조사 화면은 없다

행동을 성격에 따라 분산한다.

| 행동 | 실행 위치 |
|---|---|
| 장소 수색 · 고정물 조사 · 시신 검사 | **평면도에서 직접 클릭** |
| 소지품 검사 · 통화내역 조회 | **용의자 카드** |
| 알리바이 대조 | **관계 그래프에서 2인 선택** |

목록에서 "창고"를 고르는 것과 지도에서 창고를 누르는 것은 완전히 다른 경험이다. 조사에는 공간적 근거가 있어야 한다.

### 7.2 조사 대상은 예산의 3배 이상

```
조사 대상 ≥ 예산 × 3
```

비율이 낮으면 "무엇을 조사할까"가 선택이 아니라 소거가 된다. 산장 사건은 23개 / 예산 5 = 4.6배.

`empty`·`exclusion` 결과가 많아도 무방하다. 빈손도 배제 정보다.

### 7.3 조사 결과에는 서술이 붙는다

명사만 던지면 스프레드시트이고, 2~3문장 서술이 붙으면 수사물이다. 이 게임의 몰입은 텍스트에서 나오므로 조사 구간이 텍스트 사막이 되면 안 된다.

**물증 카드 기록은 3인칭 관찰만.** `위조` `가명` `밀폐` 같은 목적·기능 판정 단어를 쓰지 않는다. 그것은 플레이어가 내릴 결론이다.

## 8. 프로덕션 구현 범위

**프로토타입은 Claude Design 런타임(DC)이므로 배포 대상이 아니다.** Claude Code는 프로덕션 스택으로 재구현한다.

### 8.1 1차 범위 — 프로토타입과 동등하게

플레이테스트에서 검증된 것을 그대로 옮긴다. **여기서 새 기능을 더하지 않는다.**

| | 비고 |

| | 비고 |
|---|---|
| 진입 흐름 | 프롤로그 → 브리핑 → 진술 정독 → 자유 |
| 진술 정독 | D안 조판. 좌측 레일 + 본문 |
| 평면도 | 공간 조사 실행 + 조사 상태 누적 |
| 용의자 카드 | 인물 조사 실행 + 발견 단서 |
| 물증 카드 | 기본 2필드 (발견 · 기록) |
| 보고서 | 서술 단독. 5장 19공란. 순차 잠금 · 재개봉 1회 |
| 조사 기록 | 전문 보존 |
| 우측 디테일 패널 | 진술 / 조사 기록 / 메모 |
| 결말 | 서사 위 · 채점 아래 |
| 산장 사건 1건 | |
| 홈 · 사건 상세 | 프로토타입에 있음 |
| 격자(도식) · 관계 그래프 · 상황판 | 프로토타입에 있음 |
| 하이라이트 · 인용 · 메모 | 프로토타입에 있음 |

**플레이테스트에서 "안 쓰이더라"는 결과가 나온 기능은 옮기지 않는다.** 특히 격자·상황판·관계 그래프가 후보다.

### 8.2 프로덕션에서 새로 필요한 것

프로토타입에 없고 배포에 필요한 것들이다.

| | 비고 |
|---|---|
| 저장소 3분리 | 1장. **프로토타입은 단일 상태 객체** |
| 이어하기 · 진행 저장 | `CaseProgress` |
| 사건 파일 외부화 | `Case`를 정적 파일로 분리. CDN |
| 레이아웃·로직 분리 | 2장. 모바일 대비 |
| 빌드 · 배포 파이프라인 | 웹 + Tauri(스팀·데스크톱) |

### 8.3 뒤로 미루는 것

| | 이유 |
|---|---|
| 순위표 · 성향 프로필 | 사건 1건으로는 무의미. 서버 필요 |
| 아이콘 세트 · 사운드 | 증폭기. 자산 조달 필요 |
| 모바일 레이아웃 | 재설계. 플레이테스트 이후 |
| 몽타주 초상 | v1.5 |
| 생성기 · UGC 에디터 | 검증기 신뢰도 확보 후 |
| 협동 모드 | v2. 유일하게 서버가 필요한 기능 |

**증폭기를 먼저 만드는 것이 이 단계의 전형적 실패다.** 아이콘과 사운드는 재미를 만들지 않고 증폭한다.

## 9. 플레이테스트에서 측정할 것

**프로덕션 구현 전에 수행한다.** 프로토타입을 단일 파일로 export해 4명이 각자 산장 사건을 푼다.

| 질문 | 왜 중요한가 |
|---|---|
| 진행자 없이 재미있는가 | **가장 큰 미검증 가정** |
| 몇 회에 풀었는가 | 검증기 예측 5회. **어긋나면 난이도 공식 전체를 보정** |
| 부문별 성향이 갈리는가 | 부문 채점 · 순위표 · 협동 매칭의 전제 |
| 순차 잠금이 답답한가 긴장인가 | 베타 피드백으로 복원한 것 |
| 완전 침묵이 가혹한가 | 모순 경고까지 제거한 결과 |
| 격자·상황판·관계 그래프를 실제로 쓰는가 | **안 쓰이면 프로덕션에서 제외** |
| 어디서 지루한가 | |
| 진술 5개가 머리에 들어오는가 | 격자 의존도 판단 |

**두 번째가 생성기의 신뢰도를 결정한다.** 현재 기대 경로 공식은 `단서추종 × 1.5`인 임시값이며, 실측 데이터가 없으면 생성 사건의 난이도를 신뢰할 수 없다.
