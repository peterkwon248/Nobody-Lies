## 0. 이 앱이 무엇인가 (배경)

한국식 「크라임씬」 추리 게임. 플레이어는 수사관이 되어 다섯 용의자 중 범인을 찾는다.

**핵심 명제 둘** (게임의 태그라인이자 규칙):

```
① 범인만 거짓말을 할 수 있다      (범인의 모든 말이 거짓은 아니다. 진실과 섞는다)
② 무고한 사람은 진실만 말한다      (다만 모든 진실을 말하지는 않는다 — 자기 비밀은 숨긴다)
```

**설계 원칙**: 앱은 AI API 를 쓰지 않는다. 런타임 LLM 0. 논리·규칙·판정은 전부 내부 코드가
하고, LLM 은 **빌드 타임에 사용자가 자기 챗봇에 복붙**하는 방식으로 산문만 만든다.

**사건이 생기는 길은 셋**:
```
① 손저작    사람(또는 클로드코드)이 YAML 을 직접 쓴다
② 생성기    씨앗 → 코드가 논리 골격을 만든다        ★ 유저가 혼자 만드는 길
③ 들여오기  자유 텍스트 → 코드가 게임화 층          ★ 아직 없음
```
**브리프(산문 의뢰서)는 ①②가 같이 쓴다.** 논리가 서면 그 위에 산문을 입힌다.

## 1. 정확도 목표의 정의 — 「100%」가 무엇인가

이게 이 프로젝트에서 최근에 정리된 가장 중요한 것이다.

```
A  결함 0                        게임 규칙이 유한하고 관측 채널도 유한하니 곱이 유한하다
                                 → 셀 수 있다. 다만 「플레이해야 드러나는 규칙」은 못 적는다
B  적힌 명제마다 검사가 있고,      ✓ 달성 가능하고 유지 가능
   각 검사가 실제로 문다
C  채널 × 불변식 표에 빈칸 0       ✓ 매 시점 달성 가능
```

**측정 도구**: `engine/src/matrix.ts` — 관측 채널 15 × 불변식 4 = 60칸의 표.

```
관측 채널 15   진술 문단 · 추가 진술 · 조사 목록 · 조사 결과 · 물증 카드 · 확보 단어 ·
               보고서 서술문 · 격자 · 평면도 · 관계도 · 장 전환 서사 · 프롤로그 ·
               용의자 프로필 · 장 인터루드 · 결말 화면

불변식 4       누설(조사 없이 답이 나오나) · 모순(내용이 데이터와 어긋나나) ·
               도출(묻는 답에 도달 경로가 있나) · 배선(가리키는 것이 실재하나)
```

**축을 둘로 좁혔다** (사용자 결정): **범인/용의자가 구분되는가** · **트릭·물증이 완전한가**.
재미·산문 두께·난이도 체감은 **기준에서 뺐다** — 테스터만 답할 수 있다.

## 2. 지금 몇 %인가 — 실측

### 2-1. 불변식 행렬 (`npm run matrix`)

```
✓ 완전히 덮임   17 / 44   (39%)
◐ 부분만         8        검사는 있는데 일부만 본다 (✓로 세지 않는다)
· 빈 칸         19        검사가 없다
— 해당없음      16        그 조합이 성립하지 않는다
```

**39% 다.** 그리고 이 39% 도 어제까지 **50%로 잘못 알고 있었다** — ✓ 여덟 개가
반만 덮고 있었고, 그걸 찾아 `partial` 을 도입하면서 숫자가 내려갔다.

### 2-2. 공란 증명 사슬 (`npm run proof-check`)

「이 답이 왜 유일한가」를 기계가 적을 수 있는 공란의 비율.

```
생성 사건 20건 · 공란 320    증명 320 / 320 = 100%
커밋된 4건 · 공란 61          증명  35 /  61 =  57%
```

**생성 경로는 100%, 손저작은 57%.** 손저작이 낮은 이유는 결함이 아니라 **사람이 쓴
산문에는 규칙이 안 닿기 때문**이다(규칙표가 덮는 만큼만 증명된다).

### 2-3. 빌드 게이트 — 12단 (2026-08-02 갱신)

```
typecheck · lint · yaml-check · verify · gen-check · prop-check ·
clue-check · tmpl-check · brief-check · matrix-check · port-check · build
```
`npm run build` 하나로 다 돈다. 지금 **exit 0**.

> ⏭ **여기만 08-01 이후에 바뀌었다.** `clue-check` 이 7단째로 들어갔다(08-02) —
> 생성 경로가 **증명이 서는지 묻고 안 서면 단서를 까는 루프**(`clues.ts`)를 돌게 되면서
> 그 루프가 실제로 무는지 검사한다. **두 단이다** — ① 생성 40건에 약한 공란 0 ·
> ② **이동을 심어서 실제로 무나**. ②가 없으면 ①은 **이동이 전부 죽어도 초록**이다
> (착수 시점에 이미 320/320 이라 아무것도 안 걸린다).
>
> 위 §2-1·§2-2 의 숫자는 **08-02에 다시 돌려서 그대로임을 확인했다**(행렬 17/44·부분 8·
> 빈칸 19 · 증명 320/320 과 35/61). 이 문서에서 낡았던 것은 이 절 하나였다.

## 3. 「새 캠페인을 만들어달라」면 몇 %로 나오나

경로에 따라 완전히 다르다. **실측한 결과물의 프로필:**

| | 오류 | 경고 | 공란 증명 | 진술 중앙값 | 에필로그 | 관계도 간선 |
|---|---|---|---|---|---|---|
| **손저작 + 산문 왕복** (mountain-lodge) | 0 | 4 | 11/19 | 279자 | 5/5 | 7 |
| **손저작 + 원문 이식** (practice-room) | 0 | 2 | 5/10 | 310자 | 3/3 | 없음 |
| **생성기 + 산문 왕복** (pipe-organ) | 0 | 1 | 10/16 | 298자 | 0/5 | 0 |
| **생성기 + 산문 왕복** (closing-theater) | 0 | 2 | 9/16 | 288자 | 0/5 | 0 |
| **생성기만** (산문 왕복 전) | 0 | 2 | 16/16 | **64자** | 0/5 | 0 |

### 답: 「논리는 사실상 100%, 산문은 왕복이 필요, 검사가 덮는 범위는 39%」

**나오는 것:**
- ✅ 게이트 12단 통과 · 오류 0
- ✅ 끝까지 플레이됨 (프롤로그 → 진술 정독 → 조사 → 보고서 → 채점 → 결말)
- ✅ 유일 해 · 트릭 계약 성립 · 참조 무결성 · 모든 공란 도출 가능(생성 경로)
- ✅ 평면도가 사건마다 다름 (300건 실측: 봉투 285종 · 현장 289종 · 빈자리 47%)

**안 나오는 것:**
- ❌ **산문 왕복을 안 거치면 진술이 64자**다 (손저작 기준 280~310자). 격자를 문장으로
  옮긴 수준 — *"전날 밤에는 홀에 있었습니다. / 새벽까지 자리를 뜨지 않았습니다."*
- ❌ **에필로그(결말 조각) 0개** — 생성기가 안 만든다
- ❌ **관계도 간선 0개** — 점 여섯 개만 뜬다
- ❌ **물증 카드 3개가 비어 있다** (40/40 전건에서 경고가 운다)

### ★ 가장 정직한 답

**「검사가 통과했다」와 「결함이 없다」가 다르다.** 지금 검사가 덮는 것은 **44칸 중 17칸**이다.
그러니 새 캠페인은:

```
검사되는 축 17칸에 대해서는    ≈ 100%
검사 안 되는 축 27칸에 대해서는 알 수 없다 (0%도 100%도 아니고, 「측정 안 됨」)
```

**과거 실적으로 추정하면** — 이 저장소는 게이트가 초록인 상태에서 살아 있던 결함을
반복해서 찾아왔다. 하루에 여섯 건, 여덟 건씩. 그러니 **검사 안 되는 27칸에 결함이
있다고 보는 것이 안전하다.**

## 4. 안 되는 것 · 정체된 것 (전수)

### 4-1. ★ 가장 큰 것 — 산문 층에 검사가 0이다

**명제 둘이 격자에서만 강제된다.**

```
격자 (presence/claim)   ✅ 완전하게 강제됨 (verifier §7.5)
                           무고한 자의 claim ≠ presence → 오류
                           범인이 사망 구간에 거짓이 없어도 → 오류
진술 산문               ❌ 검사 0
추가 진술               ❌ 검사 0
보고서 서술문           ❌ 검사 0
```

**그런데 산문이 상품이다.** 유저가 LLM 왕복으로 받아오는 결과물이 **무검사로 들어온다.**

**막는 것**: `statement.paragraphs: string` — 자유 텍스트다. 「이 문장이 격자와 어긋나나」는
의미 이해가 필요하다.

**시도해봤고 실패한 것**: 「어휘 봉쇄」(레지스트리 낱말을 격자와 대조) — 16건에 돌려보니
**20/20 거짓 양성**이었다. 원인 둘:
```
거리 참조점   "새벽에는 진입로에 가 있었습니다. 홀에서 걸어서 2분 거리입니다."
                        ↑ 위치 주장(맞다)      ↑ 참조점 — 주장이 아니다
합성명사      "저는 무대 옷부터 걷어야 하는 사람이라"   ← 「무대」가 위치가 아니다
```
**켰으면 전건이 빨개졌다.** 실제 위반은 16건에서 **0건**이었다 — 명제는 지켜지고 있는데
**감시가 없을 뿐**이다.

**해법 후보**: 진술을 「원자 + 표현」으로 가른다. LLM 이 원자를 문장으로 만들게 하면
봉쇄가 결정 가능해진다. **왕복 계약(브리프)까지 바꿔야 하는 큰 작업.**

### 4-2. 누설 검사가 「관측면」 없이는 헛돈다

**누설 = 조사 없이 답이 나오는 것.** 이 저장소가 가장 비싸게 물린 부류다:

```
2026-07-30  소지품 검사가 범인만 비어서 150/150 범인 지목    게이트 7단 초록이었다
2026-07-30  무고한 넷의 배제 사유 문장이 거짓                게이트 7단 초록이었다
2026-08-01  인물 공란 48개가 근거 없는 찍기                  게이트 10단 초록이었다
```

지금 대칭 축을 재보면 **07-30 부류는 닫혀 있다**:
```
44건 실측 · 범인이 유일한 극단인 비율 (우연 = 1/5 = 20%)
  그 사람 대상 조사 수 · 빈손 조사 · 결과 있는 조사 · 진술 문단 수 · 간선 수   전부 0%
  salience 최대                                                            34%  ← 조금 치우침
  진술 글자 수                                                              20%  ← 우연
```

**그런데 이 측정 자체를 내가 한 번 틀렸다** — 「그 사람을 여는 사실 수」가 100%로 나왔는데,
그건 `facts[].subject` 라는 **파일 안의 값**이지 플레이어가 보는 것이 아니다(유죄 요건이
범인에게만 서는 것 = 승리 조건). **관측면이 자료구조로 없으니 「보이는 것」과 「파일에 있는
것」을 매번 손으로 갈라야 하고, 갈랐다가 틀렸다.**

**해법 후보**: `observableOf(case) → Observation[]` — 플레이어가 보는 모든 원자를 열거하는
순수 함수. `{ channel, subject, cost, text, yields }`. 누설 검사가 전부 그 위에서 돈다.

### 4-3. 생성 경로가 반쪽이다 — 산문가가 메우는 구멍들

**산문 왕복을 거친 사건만 채워지는 것들:**

```
진술 두께      조립 64자   →  왕복 후 288~298자
물증 카드      3개가 빈다  →  왕복 후 0개
에필로그       0/5         →  (손저작만 있음. 왕복으로도 안 채워짐)
관계도 간선    0           →  (손저작만 있음)
```

즉 **「유저가 씨앗만 넣으면 캠페인이 나온다」가 아직 반쪽이다.** 논리는 코드가 100% 만드는데
산문은 0%이고, 읽을 만해지려면 브리프 3종(PALETTE·PROSE·STATEMENT) 왕복이 필요하다.

### 4-4. 아예 없는 것

```
③ 들여오기       자유 텍스트 → 게임화. 전수 grep 0건. 문 2가 안 열렸다
⑤ 검열관 LLM     「이 산문이 답을 흘리나」 — 규칙 쪽(§9-7·9-8·9-9)만 있고 LLM 쪽은 없다
결말 검사        MEMORY 가 「결말이 옛 트릭을 서술」을 미해결로 적어뒀는데 §9-7 이 결말을 안 읽는다
```

### 4-5. 정체된 것 — 코드가 아니라 사람 손

```
🎯 테스터에게 URL 을 보낸다    ★ 네 세션째 열려 있다 ★
```

**플레이테스트가 1명이고 그 1명이 사용자 본인**이다. 사용자는 범인을 알고 시작하므로
**누설을 구조적으로 못 느낀다** — 소지품 150/150 이 화면에서 안 튄 이유가 그것이다.

`docs/MANIFESTO.md` 가 적어둔 문장: *"낯선 플레이어 한 명의 한 판이 지금까지의 어떤
감사보다 크다."* 배포는 살아 있다(`https://nobody-lies-app.vercel.app/`, 4건, 폰 OK).

### 4-6. 남아 있는 작은 결함들

```
「홀로 옮겼습니다」        문법은 맞는데 「혼자서」로도 읽힌다 (뜻이 겹침)
DS 번들 createRoot 충돌   매 로드 콘솔 4건. main.jsx 주석이 「순서 운으로 이긴다」고 적어둠
사이드바 밖 클릭 요소 137곳  접근성. 일괄 치환하면 안 됨 (역할이 자리마다 다름)
closing-theater          프롤로그 불일치를 일부러 남긴 재현 테스트 — 테스터 목록에서 뺄 것
끝난 사건 표시            ✅ 08-01에 닫힘
```

## 5. 남은 27칸을 「무엇이 막고 있나」로 갈랐다

```
막는 게 없다 — 그냥 지으면 됨    약 10칸   결말 × 모순 · 인터루드 · 물증 × 모순 …
관측면 자료구조가 필요            약  6칸   누설 축 전부
왕복 계약을 바꿔야 열림           약  5칸   산문 층 (진술 · 추가 진술 · 보고서 × 모순)
기능이 덜 만들어짐                약  6칸   관계도 간선 0 · 에필로그 0 · 결말 × 배선
```

**「왕복 계약만 바꾸면 되나」의 답은 아니다** — 그건 5칸이고 나머지 22칸은 다른 것이 필요하다.

**제안한 순서**: 막는 게 없는 것 → 관측면 → 왕복 계약 → 덜 만든 기능.
이유는 둘 — 큰 구조 변경 전에 표본을 늘려야 하고, **검사 열 개가 같은 것을 각자 모으기
시작하면 그게 곧 관측면의 명세**가 된다.

## 6. ★ 이 프로젝트에서 반복해서 확인된 패턴 (브레인스토밍에 가장 쓸모 있을 것)

### 6-1. 결함은 검사가 없는 축에서만 나온다 — 우연이 아니라 필연

게이트가 초록인 채로 살아 있던 결함이 셀 수 없이 많았다. 전부 **검사가 없는 축**에서 나왔다.
검사가 있는 축은 애초에 커밋 전에 죽는다. 그래서 질문이 「어떻게 결함을 줄이나」가 아니라
**「검사되지 않는 축이 몇 개 남았나」**가 되어야 했고, 그게 불변식 행렬을 만든 이유다.

### 6-2. 정확한데 틀린 명제는 정밀도로 못 고친다

`verifier §5` 가 이렇게 계산한다:
```
combos = 인물 5 × 장소 4 × 시각 4 × 도구 4 = 320    // 30 을 넘어 통과
```
**계산은 완벽하다. 명제가 틀렸다.** 「장 전체를 한 번에 맞힐 확률」과 「각 칸이 도출 가능한가」는
다른 명제이고 **채점은 공란별**이다. 곱이 클수록 **개별 칸의 찍기를 더 잘 숨긴다** —
검사가 오히려 반대로 작동했다. 인물 공란 48개가 그 구멍으로 빠져나갔다.

### 6-3. 심어보지 않으면 검사를 믿으면 안 된다

하루에 검사가 **두 번** 개발자를 속였다:
```
① 성을 붙인 이름으로만 찾아 손저작 골든 케이스가 다섯 줄 빨개졌다
   (한국어 진술은 「한유빈」을 「유빈 언니」로 부른다)
② 고치기 전 상태를 심었는데 통과했다
   (장 전환 지문 "…남주원이 한마디를 보탰다" 가 이름을 말해서) — 지문은 증거가 아니다
```
거짓 양성은 **스스로 알린다**(빨개지니까). 놓침은 **아무 말도 안 한다** — 심어야만 잡힌다.

### 6-4. 세는 것과 확인하는 것이 다르다

2026-07-31에 「코드가 쥔 문장」을 **세어서** *"A 부류(사실을 문장으로 갖는 것)는 거의
닫혀 있었다"* 고 결론냈다. **숫자는 맞았다**(17종). 그런데 **각 주장이 무엇으로 받쳐지는지는
안 봤다.** 다시 재보니 1장이 *"[인물]이 가장 먼저 일어났다"* 고 단언하는데 세계에 기상 시각이
없었고, **지목 아닌 인물 공란 48개가 전부 찍기**였다.

### 6-5. 짓기 전에 재면 방향이 바뀐다 — 이번 세션에만 다섯 번

```
① 어휘 봉쇄        20/20 거짓 양성 → 짓기 전에 접었다
② 관계도 누설      danger 간선이 범인만 가리켜서 「누설」로 읽었는데 전부 게이트돼 있었다
③ 결말 × 모순      「막는 게 없다」고 봤는데 의미 이해가 필요했다
④ 확보 단어 × 모순  term.note ≡ evidence.record 로 봤는데 일부러 다른 짝이었다
⑤ 프롤로그 측정    ★ 내 측정 코드가 배열을 문자열로 읽어 늘 빈 값이 나왔다 ★
```

⑤가 특히 아프다 — `prologue: Text[]` 인데 `ko()` 로 읽어서 항상 `''` 였다. 그 결과
*"프롤로그가 발견 시각을 안 말한다"* 고 판단하고 `incident.sceneState` 에 중복으로 적었다.
**실제로는 프롤로그 3번째 줄이 이미 말하고 있었다**:
> *"아침, 가장 먼저 일어난 사람이 방 문을 열었다."*

**측정 코드도 코드다.** 측정이 틀리면 그 위에 쌓은 결론이 전부 틀린다.

## 7. 브레인스토밍에 던질 만한 질문

1. **산문 층을 어떻게 검사 가능하게 만들 것인가** — 「원자 + 표현」 분리가 맞나?
   LLM 왕복 계약을 어떻게 설계해야 사실 지어내기를 구조적으로 막나?
2. **관측면(Observation) 자료구조의 올바른 모양은?** 채널·비용·주체·산출을 어떻게 잡아야
   누설 검사가 전부 그 위에서 돌 수 있나?
3. **「플레이해야만 드러나는 규칙」을 줄일 방법이 있나** — 지금은 테스터만 답할 수 있는
   영역으로 분류했는데, 그중 일부는 대리 지표로 잴 수 있지 않나?
   (선택의 분산 · 정보 도착 리듬 · 레드 헤링 매력도)
4. **생성 경로의 산문을 코드가 어디까지 만들 수 있나** — 지금 64자인데, 이름·호칭·물음표·
   문형 다양화는 코드로 가능하다(팔레트에 재료가 이미 있다). 어디까지가 코드 몫인가?
5. **변이 시험(mutation testing)을 어떻게 도입할 것인가** — 지금 「심어서 확인」이 사람 손이다.
   사건 데이터를 기계로 변이시켜 「빠져나간 변이 K/N」을 인쇄하면 검사를 검사할 수 있다.
