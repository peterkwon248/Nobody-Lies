# 기본 디자인 감사 — 인계 지시서 (Claude Code)

> ⛳ **안착 경위** (2026-08-05): 이 지시서는 챗에서 만들어졌으나 저장소에 들어오는
> 마지막 한 걸음(다운로드 → 커밋)에서 **세 번 증발**했다. 세 번째에 구간 자체를
> 빼고 **붙여넣기로 우회**해 여기 안착했다. — `~/.claude` 메모리
> `specs-live-in-the-users-head` 참조.

**목적**: 도시에 스킨(온도 층)을 입히기 전에 기본층(Vector 기반 클린 미학)을
심화한다. 이 지시서는 그 첫 걸음인 **감사(측정)**다 — 수리가 아니다. 산출물은
「고칠 자리 목록」이고, 우선순위는 사용자가 표를 보고 찍는다. 감사 없이 심화를
시작하면 끝없는 폴리싱 늪이 된다 — **감사가 만든 유한 목록이 늪의 방벽이다.**

**순서 (사용자 확정)**: UI 재균형 배치 → **이 감사** → 수리 배치 → 도시에 스킨.
재균형 배치(⓪~③ + REMOVED)가 아직 열려 있으면 이 지시서는 대기다.
→ ✅ **재균형은 2026-08-05 완결됐다** (`5cb0198`~`8e64fe5`). 이 감사는 **착수 가능**하다.

★ **이번 감사의 고정 원칙: 모든 축을 모든 뷰포트에서 잰다.** 데스크톱에서 옳은
위계가 모바일에서 무너지면 그건 두 결함이 아니라 **「반응이 안 되는 위계」라는 한
결함**이다. **축 × 뷰포트가 감사의 단위다.**

## 0. 측정 환경 — 뷰포트 4폭 고정

```
mobile     375 × 812    (iPhone 기준 최소폭 — 테스터 다수가 여기다)
tablet     768 × 1024
laptop     1280 × 800
desktop    1536 × 960
```

- 캡처는 Playwright 헤드리스로 자동화한다(Azgaar 파이프라인에서 쓰던 그 경로).
  스크립트를 `scripts/` 에 남겨 **재실행 가능**하게 — 수리 후 같은 스크립트로
  전후 비교하는 것까지가 이 스크립트의 수명이다.
- **대상 화면 전수**: 프롤로그 인터루드 · 진술(카드/목록) · 격자 · 평면도 ·
  조사 목록 · 물증/확보 단어 · 각 장 서술문+공란 · 보고서 작성 · 제출/지목 ·
  에필로그 · 설정. **라우트가 아니라 상태로 갈리는 화면**(빈 상태 · 진행 중 ·
  완료)도 각각 캡처한다.
- 캡처 파일명: `{화면}-{상태}-{뷰포트}.png` — 표에서 참조하는 키다.

## 1. 감사 축 다섯 — 각 축을 4폭 전부에서

### 축1 타이포 위계

- 화면에 실재하는 (font-size · weight · line-height · letter-spacing) 조합을
  **전수 수집**한다 (computed style 크롤링 — **눈이 아니라 코드로**).
- 조합이 몇 개인가. 목표는 역할이 고정된 4~5단인데 **현재 몇 단이 실재하고**,
  같은 역할(예: 카드 제목)이 화면마다 다른 조합을 쓰는 자리는 어디인가.
- **뷰포트별**: 각 단이 375 에서 몇 px 로 렌더되나 — 본문이 14px 미만으로
  떨어지는 자리, 제목이 줄바꿈으로 위계가 무너지는 자리.

### 축2 밀도의 완급

- 화면을 두 부류로 분류한다: **도구 화면**(격자·조사·물증 — 촘촘해도 된다) /
  **서사 화면**(인터루드·서술문·지목 — 성겨야 한다).
- 부류별 실측: 행 높이 · 패딩 · 화면당 정보 항목 수. **두 부류의 밀도가 실제로
  갈리는가**, 아니면 전 화면이 같은 완급인가.
- **뷰포트별**: 375 에서 도구 화면이 가로 스크롤·겹침·잘림을 내는 자리 전수.
  (재균형 배치가 평면도·카드를 고쳤으니 **그 외에서 남은 것**을 찾는 것)
- ★ **중간 공개의 무게** (2026-08-05 사용자 결정 반영 · `docs/DESIGN-NOTES.md`
  참조): 추가 단서 공개 · 트릭 인상 붕괴 · 장 전환이 **현재 어떤 무게로
  렌더되는지** 4폭에서 캡처하고, 프롤로그/에필로그의 전체 화면 인터루드 문법과
  대비해 표에 적는다. **측정만** — 수리안(전체 화면 승격)은 수리 배치의 몫이다.

### 축3 상태의 문법

- 인터랙티브 요소 전수에 대해: hover · focus-visible · 선택 · 비활성 · 로딩 ·
  빈 상태가 **정의돼 있는가, 화면마다 다른가.**
- **빈 상태는 별도 절로**: 확보 단어 0 · 조사 전 물증칸 · 공란 미기입 —
  추리게임에서 「비어 있음」은 공백이 아니라 **「아직 모른다」는 정보**다.
  지금 그 자리들이 무엇을 렌더하는지 캡처.
- **모바일 전용**: hover 의존 UI(터치에서 도달 불가한 기능)가 있는가 — 이건
  반응형 결함 중 **최상급**이다. 터치 타깃 44px 미만 전수.

### 축4 모션 문법

- transition/animation 전수 수집: 어디에 · duration · easing.
  `design-quality-gate` 의 duration 규칙과 대조 — **규칙 밖 값 전수.**
- 사건의 순간 셋(카드 등장 · 단어 확보 · 장 전환)에 모션이 있는가 없는가.
  **판단하지 말고 유무만** — 무엇을 넣을지는 수리 배치의 저작 판단이다.
- `prefers-reduced-motion` 대응 유무.

### 축5 토큰 규율

- Plot 감사의 게임판: **하드코딩 hex · 인라인 스타일 · Vector 토큰 밖 값 ·
  strokeWidth 불일치 · 간격 그리드(4/8px) 위반**을 **파일:줄 단위로 전수.**
- **이 축이 도시에 스킨의 선행 조건이다** — 하드코딩이 있는 자리는 `--game-*`
  폴백을 끼울 **토큰 자리가 없다.** 스킨 지시서 §7 이 예고한 그 목록을 여기서
  미리 만든다.
- 미디어쿼리/뷰포트 분기 전수: 몇 개의 breakpoint 가 실재하고 서로 일관한가,
  아니면 화면마다 임의 px 인가.

## 2. 산출물 — 표 하나, 판단 없이

`docs/DESIGN-AUDIT-2026-08.md` 로:

```
| # | 축 | 화면(캡처 키) | 뷰포트 | 실측 | 심각도 |
```

- **심각도만 기계적 기준으로 단다** — **깨짐**(사용 불가·도달 불가·잘림) /
  **어긋남**(문법 불일치·규칙 위반) / **밋밋함**(기회 — 결함 아님).
  **무엇을 먼저 고칠지는 달지 않는다** — 그것이 사용자가 찍을 우선순위다.
- 표 위에 **요약 수치**: 타이포 조합 수 · 하드코딩 건수 · breakpoint 수 ·
  터치 타깃 위반 수 · 빈 상태 미정의 수. **수리 후 같은 수치를 다시 재는 것이
  진척의 실측**이 된다.
- 구조 리팩터링이 필요해 보이는 항목은 **고치자고 쓰지 말고 §구조 백로그 절에
  따로 모은다** — 언젠가 올 UI 재작성의 입력이지 이번 수리의 범위가 아니다.

## 3. 하지 않는 것

- **수리** — 이 지시서는 측정만이다. 감사 중 한 줄짜리 수정이 보여도 고치지 말고
  표에 적는다 (**고치기 시작하면 감사가 안 끝난다**)
- `App.jsx` 구조 변경 · 컴포넌트 분리
- 새 breakpoint 체계 설계 (그건 수리 배치의 일 — 여기선 현황만)
- 스킨·색·서체 논의 (도시에 스킨 배치의 일)
- 엔진 접촉 (**이 감사는 `app/` 에 갇힌다.** 게이트는 마지막 확인용 1회)
