# Ⅰ. 원칙 (원문)

## 1. 개발 철학

앱은 최대한 단순하고, 검증 가능하며, 유지보수하기 쉬워야 한다.

AI는 앱을 대신 실행하는 존재가 아니라, 앱 제작을 돕는 협업자이다.

따라서 앱의 핵심 기능은 항상 내부 코드가 담당하고, AI는 사람이 하기 번거로운
창작·정리·확장 작업만 담당한다.

## 2. 구현 우선순위

새로운 기능을 만들 때는 항상 아래 순서를 따른다.

1. 기존 코드 재사용
2. 검증된 오픈소스 활용
3. 기존 라이브러리 조합
4. 직접 구현
5. SVG·커스텀 그래픽 제작

절대로 처음부터 모든 것을 새로 만들려고 하지 않는다.

## 3. 오픈소스 우선 원칙

동일한 기능을 제공하는 오픈소스가 존재한다면 직접 구현보다 오픈소스 활용을
우선한다. 단,

- 라이선스가 명확해야 한다.
- 유지보수가 활발해야 한다.
- 장기적으로 수정 가능한 코드여야 한다.
- 프로젝트 구조와 충돌하지 않아야 한다.

## 4. 앱은 AI 없이 완전하게 동작해야 한다

모든 핵심 기능은 오직 내부 코드만으로 동작해야 한다.
외부 LLM이 없더라도 앱은 정상적으로 사용할 수 있어야 한다.
AI API가 없다고 앱이 멈춰서는 안 된다.

## 5. 내부 코드의 역할

다음은 반드시 내부 코드가 담당한다.

데이터 구조 · 비즈니스 로직 · 계산 · 검증 · 저장 · 검색 · 정렬 · 필터링 ·
랜덤 생성 · 규칙 처리 · 게임 로직 · 상태 관리 · UI 동작 · 데이터 변환 · 파일 입출력

즉, **정확성이 필요한 모든 것은 내부 코드가 담당한다.**

## 6. LLM의 역할

LLM은 창작과 언어 작업만 담당한다.

문장 작성 · 요약 · 번역 · 캐릭터 설정 확장 · 세계관 확장 · 스토리 작성 ·
설명 작성 · 표현 개선 · 아이디어 생성 · 브레인스토밍

**LLM은 앱의 규칙을 결정하지 않는다.**

## 7. 브리프(Brief) 시스템을 기본으로 한다

모든 AI 기능은 브리프를 통해 이루어진다.
브리프는 **내부 코드가 생성하는 LLM 전용 작업 지시서**이다.
기능마다 각각의 브리프를 가진다.

예) 시나리오 생성 · 세계관 생성 · 노트 요약 · 캐릭터 작성 · 문서 작성 ·
설명 생성 · 데이터 분석

## 8. 사용자의 LLM을 활용한다

앱은 **AI API를 기본적으로 사용하지 않는다.**
대신 사용자가 쓰는 ChatGPT · Claude · Gemini · Kimi 등 원하는 LLM을 자유롭게
쓸 수 있도록 돕는다.

```
앱 → 브리프 생성 → 사용자가 원하는 LLM에 붙여넣기 → LLM 결과 생성
   → 앱에 다시 붙여넣기 → 내부 코드가 검증 및 적용
```

## 9. 내부 코드가 항상 최종 검증한다

LLM의 결과를 그대로 신뢰하지 않는다. 반드시

스키마 검사 · 형식 검사 · 누락 검사 · 중복 검사 · 규칙 위반 검사 · 참조 오류 검사

를 수행한다. **오류가 있으면 수정 브리프를 다시 생성한다.**

## 10. 데이터는 구조화한다

LLM과 주고받는 데이터는 가능한 한 JSON · YAML · Markdown · CSV 등 구조화된
형식을 사용한다. 자유 형식의 텍스트는 최소화한다.

## 11. AI는 선택 기능이다

AI는 앱을 더 강력하게 만들어주는 기능일 뿐 앱의 필수 기능이 되어서는 안 된다.
AI를 전혀 사용하지 않아도 앱은 정상적으로 동작해야 한다.

## 12. 유지보수성을 최우선으로 한다

코드는 짧은 것보다 읽기 쉬운 것을 우선한다.
복잡한 기술보다 오래 유지 가능한 구조를 우선한다.

## 13. 범용성을 우선한다

특정 앱만을 위한 기능보다 다른 프로젝트에서도 재사용 가능한 구조를 선호한다.
컴포넌트 · 유틸리티 · 엔진 · 모듈 · 브리프 생성기 등은 가능한 범용적으로 설계한다.

## 14. AI에게 맡기지 말아야 할 것

핵심 알고리즘 · 보안 · 권한 처리 · 데이터베이스 설계 결정 · 비즈니스 규칙 ·
**게임 판정** · 계산 결과 · 중요한 상태 변경

이들은 반드시 내부 코드가 수행한다.

## 15. AI에게 적극적으로 맡길 것

문장 생성 · 문체 개선 · 설정 확장 · 세계관 구축 · 이름 추천 · 설명 작성 ·
문서 초안 · 요약 · 아이디어 제안 · 데이터 해석 · 브레인스토밍

## 16. 최종 목표

좋은 앱은 AI가 있어야만 동작하는 앱이 아니다.
좋은 앱은 내부 코드만으로 완성되어 있으며, AI는 그 위에서 창작과 생산성을
극대화하는 협업 도구가 된다.

> ## 핵심 원칙 (한 줄 요약)
>
> **«코드는 사실·구조·규칙을 책임지고, LLM은 표현·창작·확장을 책임진다.
> 둘은 브리프 시스템으로 연결된다.»**

# Ⅱ. 이 저장소에 적용하기

> 여기부터는 저장소 쪽 해설이다. **원칙이 바뀌면 이 절을 고친다 — 반대가 아니다.**

## 가름 축 — 「무엇과 대조하면 틀렸다고 말할 수 있나?」

> ⚠ **「판정」이라 부르지 않는다.** 이 저장소에서 그 말은 §절대 규칙과 §14 의
> **게임 판정**을 뜻한다. 섞이면 위험하다 — 셋은 전혀 다른 일이다:
>
> | | 무엇 | 누가 |
> |---|---|---|
> | ① **게임 판정** | 플레이어의 답이 맞았나 | **언제나 코드.** LLM 금지(§14) |
> | ② **누설 판정** | 이 산문이 답을 흘리나 | LLM 이 **경고**, 코드가 처리(⑤검열관) |
> | ③ **가름** | 이 값이 사실인가 표현인가 | **개발 시점.** 플레이와 무관 |
>
> 아래는 **③**이다. 플레이어는 이것을 평생 보지 않는다.
> 그리고 ③도 매번 하지 않는다 — **한 번 갈라서 코드에 선언하면 그 뒤로 기계가
> 문다**(`world-check` 의 `UNIVERSAL`, `port-check` 의 `APP_ONLY`).

§16 의 한 줄 요약을 실무에서 쓰려면 **사실과 표현을 가르는 시험**이 필요하다.
말로 가르면 매번 헷갈린다. 이 질문 하나면 갈린다:

> **이 값이 틀렸다고 말하려면 무엇과 대조해야 하나?**
>
> - **대답이 있다 → 사실이다.** 코드가 갖는다. **그리고 그 대답이 곧 이 값이
>   가져야 할 꼴이다.**
> - **대답이 없다 → 표현이다.** LLM 이 갖는다. 코드는 **자리만** 만든다.

두 번째 문장이 핵심이다. 「사실이니 코드가 갖는다」로 끝나면 **오늘의 버그가
그대로 재발한다** — 사실을 코드가 갖긴 했는데 **문장으로** 가져서 대조가 불가능했다.

```
'아침에 함께 도착했다'  →  무엇과 대조?  people[].presence
                        →  그러니 presence 를 가리키는 구조여야 한다
                        →  basis: { kind: together, slot: LAST, at: hall }

'최장/최단 2.46배'      →  무엇과 대조?  engine/cases/mountain-lodge.yaml
                        →  그러니 재서 채워야 한다 (voice-check 가 이미 잰다)

'화장대 전등이 켜진 채였고…'  →  무엇과 대조?  없다. 취향이다
                              →  LLM 몫. 코드는 result.body 자리만 만든다
```

## 어긋나는 세 가지 꼴

```
❌ A  사실을 코드가 「문장으로」 갖는다      검사할 대상이 없다
      '아침에 함께 도착했다'                ← 2026-07-30 발견 · 생성 사건 전건

❌ B  사실을 LLM 이 정한다                 지어낸다
      CASE-BRIEF 가 이미 막는다 — 논리를 얼리고 나서 산문을 얹는 이유

❌ C  표현을 코드가 갖는다                 100건이 같은 문장이 된다
      '그날 아침' — 팔레트가 밤 시각을 주면 어긋나기까지 한다
```

> ★ **A 와 C 는 한 줄에서 동시에 일어난다.** `'그날 아침 [인물]이 가장 먼저
> 도착했다'` 는 사실(도착 여부)을 문장으로 갖고(A), 동시에 문안(표현)을 코드가
> 쥐고 있었다(C). **한 줄이 두 가지로 틀렸다.**

**B 는 이미 막혀 있다.** A·C 가 남은 일이다.

> ★★ **A 는 「거의 닫혔다」가 아니었다 — 세는 것과 확인하는 것이 다르다** ★★ (2026-08-01)
>
> 07-31에 코드가 쥔 문장을 **세어서** *"A 부류는 거의 닫혀 있었다"* 고 결론냈다.
> 숫자는 맞았다(17종). 그런데 **각 주장이 무엇으로 받쳐지는지는 안 봤다.**
> 다시 재보니 1장이 *"[인물]이 가장 먼저 일어났다"* 고 단언하는데 **세계에 기상 시각이
> 없었고**, 무고한 넷이 산문에서 완전 대칭이라 **지목 아닌 인물 공란 48개가 전부 찍기**였다.
>
> **A 의 시험은 「이 문장이 몇 개인가」가 아니라 「이 주장을 무엇과 대조하나」다.**
> 위 §가름 축이 처음부터 그렇게 적어놨는데, 세는 도구(③)를 만들고 나서 **도구가 세는
> 것을 시험으로 착각했다.** 닫은 방식과 검사는 `MEMORY.md` §페어플레이 규칙에 있다.

## 사건이 생기는 길은 셋이다 — 생성기는 그중 하나다 (2026-07-31 사용자 확정)

> **생성기는 「유저가 혼자 만드는 길」이다. 내가 만들 때는 안 거쳐도 된다.**
>
> 사용자 확정: *"클로드코드로 디테일한 캠페인을 만들 땐 생성기가 꼭 필요한 게
> 아니잖아. 생성기 = 유저가 직접 캠페인을 만들게 하기 위해 필요한 것."*

```
① 손저작    사람 · 나(클로드코드)가 YAML 을 직접 쓴다   mountain-lodge · practice-room
② 생성기    씨앗 → buildWorld + buildGameLayer         ★ 유저용 · Generator.jsx
③ 들여오기  자유 텍스트 → 코드가 게임화 층             문 2. 아직 없다
                        ↓ 셋이 여기서 만난다
                parseCase + verifier 판정    ← §9 · §14. 어느 길로 왔든 같다
```

**게이트가 이미 둘을 따로 검사한다** — `gen-check`(생성기 40건 100%) 와
`tmpl-check`(`case-template.yaml` = **손저작 서식**) 는 **별개 단**이다.
손저작은 게이트에 정식으로 한 자리를 갖고 있다. **생성기의 부속물이 아니다.**

**커밋된 4건 중 둘이 생성기를 안 거쳤다** — `mountain-lodge`(손글씨 레퍼런스) ·
`practice-room`(사용자의 오프라인 텍스트를 손으로 옮긴 것). **절반이 반례다.**

> ⚠ **어느 길로 왔는지 기록하는 필드가 없다.** `prose.source: authored` 는 넷 다
> 붙어 있는데 그건 **산문**의 출처지 사건 골격의 출처가 아니다. 문서만 뭉갠 게 아니다.

### ⚠ 그래서 §5·§6 을 저작자에게 걸지 않는다

아래 §들여오기 절의 *"LLM 에게 YAML 전체를 쓰게 하면 안 된다"* 는
**앱 파이프라인 안의 LLM** 에 대한 규칙이다 — 유저가 자유 텍스트를 넣었을 때
게임화 층은 **코드**가 지어야 한다는 말이다. **저작자에게 거는 말이 아니다.**

```
앱이 부르는 LLM      사실·규칙을 지어내면 아무도 안 본다   → §5·§6 이 막는다
저작자(나 · 사용자)   게임화 층까지 직접 쓴다              → verifier 가 판정한다
```

`practice-room` 은 **내가 게임화 층 112개를 손으로 다 써서** 게이트를 통과했다.
그것이 §5 위반이었으면 **`tmpl-check` 도 위반이다** — 저 서식도 사람이 쓴 게임화 층이다.

> **원래 결정이 이것이었다.** `design-brief.md:442` 가 *"생성기는 일일 사건 규모만
> 담당한다 … 캠페인은 사람이 쓴다"* 고 못박아뒀다
> (`MEMORY.md` §캠페인 자동 생성 — 경계가 밀렸다). 07-29에 **규모** 경계가
> 넘어가면서 그 줄 전체가 낡은 것처럼 읽히게 됐지만, **「campaign 은 사람이 쓴다」는
> 그대로 살아 있다.** 새 결정이 아니라 묻혔던 결정이다.

### ⚠ 문서 어긋남 — 「빌드 타임 LLM 4곳」 목록이 실물과 다르다

`MEMORY.md:105` · `HANDOFF-TO-CODE.md:71` · `SYSTEM-DECISIONS.md` 가

## 이 원칙이 이미 값을 한 자리 (2026-07-30)

무고한 넷의 배제 사유가 `'아침에 함께 도착했다'` 였다. 생성기의 구조는
「모였다 → 흩어졌다 → 다시 모였다」라 **넷은 밤새 건물 안에 있고 아무도 아침에
도착하지 않는다.** 자기 진술이 그렇게 말하는데 1장 보고서는 그 반대를 썼다.

- **게이트 7단이 내내 초록이었다** — 배제는 `e_mutual` 이 기계적으로 받치므로
  거짓인 것은 **사유 문장뿐**이었고, 문장은 검사 대상이 아니었다
- **뿌리는 산장의 문구를 전제 없이 가져온 것** — 산장은 넷이 실제로 오전에
  도착하고 격자의 밤 슬롯이 부재다. 생성 세계는 부재가 없다
- **UGC 가 상품이므로 이건 개발자 불편이 아니다** — 사용자가 만드는 **모든
  사건**이 이 거짓 위에 지어진다

**한 줄 요약이 이 버그를 정확히 서술한다** — 코드가 사실을 책임져야 하는데,
사실을 **문장으로** 쥐고 있어서 책임질 수가 없었다.

## 이 원칙이 값을 한 두 번째 자리 — 들여오기 (2026-07-31)

사용자가 *「예전에 오프라인으로 플레이한 추리 텍스트도 캠페인화 가능한가」* 를 물었다.
**옮겨봤다** — 「연습실 편」을 손으로 YAML 로 만들어 검증을 통과시켰다.

```
원문에서 온 것  64   격자 · 거짓말 · 진술 · 인물 · 장소 · 범인 · 핵심 물증
지어낸 것      112   조사 · 공란 · 보고서 · 레드헤링 · 예산 · salience
```

**지어낸 112가 전부 한 층에 몰려 있었다 — 게임화 층.** 그리고 검증기가 낸 오류 둘도
둘 다 그 층이었다. **논리 골격은 손도 안 대고 통과했다.**

> ⛳ **아래 문단은 「③ 들여오기」 길에만 걸린다** — 유저가 자유 텍스트를 넣는 경우다.
> **손저작(①)에는 안 걸린다.** 위 §사건이 생기는 길은 셋이다 참조.

여기서 §5·§6 이 설계를 정한다. 「LLM 에게 YAML 전체를 쓰게 하자」가 자연스러워 보이는데
**그러면 조사 구성·예산·salience·레드헤링 배치를 LLM 이 정하게 된다.** 그건 §5 가
코드 몫이라 못박은 **게임 로직**이고, §14 의 **게임 판정** 바로 옆이다.

```
자유 텍스트 → LLM → 진실 세계만 → 코드가 게임화 층 → parseCase + verifier 판정
                     §6 표현·이해     §5 규칙            §9 · §14
```

**LLM 이 쓸 것이 3분의 1로 줄고, 줄어든 쪽이 정확히 「지어내면 위험한 쪽」이다.**
원칙이 없었으면 「LLM 이 다 해주니 편하다」로 갔을 자리다.

> 그래서 `generateCase` 를 `buildWorld` + `buildGameLayer` 로 갈랐다(2026-07-31).
> **이 두 함수의 경계가 곧 §6 과 §5 의 경계다.**
