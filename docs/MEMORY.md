## 이게 뭔가

정지된 살인 사건 하나(산장 살인사건)를 플레이어(무명의 수사관)가 **진술 정독 → 제한된 조사 → 보고서 공란 채우기**로 푸는 추리 게임.

계보는 Return of the Obra Dinn → The Case of the Golden Idol. 차이는 **사건을 논리 검증기로 검사해 자동 생성할 수 있다는 것.** v1은 손으로 쓴 산장 사건 1건.

- **앱 이름**: 노바디 라이즈 (Nobody Lies)
- **저장소**: https://github.com/peterkwon248/Nobody-Lies (public)
- **현재 단계**: 설계 완료 · 프로토타입 완성 · **플레이테스트 이전** · 프로덕션 코드 0줄

핵심 규칙이 곧 제목이다 — *무고한 사람은 거짓말하지 않는다. 다만 자기 비밀은 말하지 않는다.* 그리고 제목 자체가 거짓이다. 다섯 중 하나는 거짓말을 한다.

## 절대 규칙 — 새 화면·기능마다 확인할 것

> **게임이 플레이어의 판단에 대해 하는 말은 최종 채점 하나뿐이다. 그 전까지 완전한 침묵.**

이 게임의 상품은 "내가 알아냈다"는 감각이다. 아래를 위반하면 상품이 사라진다.

| 금지 | |
|---|---|
| 실시간 채점 | 장을 완성해도 정답 여부를 알리지 않는다 |
| 모순 경고 | "확보한 물증과 어긋납니다" 없음 |
| 게임이 하는 텍스트 강조 | 볼드·하이라이트·색칠 |
| 유용도 시각 구분 | 결정적 단서와 레드 헤링이 완전히 동일하게 생겨야 함 |
| 프로필의 유죄 판정 | 사실만. `기회 있음 ✓` 금지 |
| 조사 추천·힌트 | 없음 |
| 자동 분석 일체 | 모순 탐지·타임라인 해석 등 |

**이 규칙은 개발 중 일곱 차례 다른 형태로 재발했다** (배너 → 진술 볼드 → 프로필 판정 → 분석 보조 토글 → 모순 경고 → 물증 카드 `뜻` 필드 → 격자 자동 추출). 전부 "친절한 UI의 기본값"에서 나온다. 보통 앱은 중요한 것을 강조해주는 게 미덕이지만 이 게임에서 그것은 정답 누설이다.

부수 규칙 둘:
- **한 번 보여주고 사라지는 텍스트는 버그다.** 토스트는 "어디에 새 것이 생겼다" 신호만. 내용은 해당 화면에 영구히.
- **런타임 LLM은 0이다.** 예외 없음. 빌드 타임 4곳만(진술 산문 / 프롤로그 / 번역 / UGC 누설 검사), 결과는 파일에 고정.


`after-work`가 이걸 커밋 게이트로 쓴다. 지금 단계에서 가장 의미 있는 게이트는 "사건 데이터가 여전히 논리적으로 성립하는가"이므로 이렇게 걸었다. `app/`이 생기면 앱 빌드를 앞에 붙인다.

## 엔진 ↔ 프로토타입 데이터 불일치 (미해결)

같은 산장 사건이 두 곳에 있는데 어긋난다. **지금 검증기는 실제로 플레이되는 사건을 검증하지 않고 있다.**

1. ~~**4장 공란 답이 다름**~~ — **해소됨 (2026-07-24)**

   | 공란 | 결정 | 근거 |
   |---|---|---|
   | 협박대상 | **조유리** | 프로토타입 답(김채원)은 자기 문장틀("조직은 ___의 입을 막으려 했고")에선 맞지만, 그 자리는 5장 동기 `폭로 임박`과 같은 사실을 두 번 묻는다. 조사 0회로 채워지는 공란이었고, 유료 조사(`유리의 협박 문자`·`소지품 검사 · 조유리`)가 답안지에 흔적을 안 남겼다. 엔진이 검증한 기대 5회가 이미 `yuri` 기준이라 예산 중립. **답이 아니라 문장틀을 고쳤다** → "조직은 {조유리}를 약물로 붙들어 두고 있었고" |
   | 인물 | **장원영** (프로토타입 쪽) | 엔진은 4장 인물을 `sakura`로 두고 `requiresFacts`에 `f_sakura_is_alias`까지 걸어놔서, **정체를 알아야 열리는 장에서 그 정체를 답으로 쓰는** 구조였다. 5장 범인 지목이 요식행위가 된다. `f_sakura_is_alias`를 5장 `requiresFacts`로 옮기고 정체 폭로를 5장 에필로그로 이동 |

   > 이전 기록에 있던 "4장을 5공란으로 늘려 둘 다 넣는다"는 **논의 중이던 안이 결정으로 잘못 적힌 것**이었다. 채택하지 않았다 — 사쿠라를 4장에 중복 배치하면 클라이맥스가 한 장 앞당겨진다.

1-1. **`공범` 라벨 폐기 (2026-07-24)**

   심증 부문을 늘릴 후보로 `공범`(김채원)을 검토했으나 **공란 어휘에서 아예 제거했다.**

   - **누설** — 라벨 존재 자체가 "범인 말고 한 명 더 있다"를 조사 0회에 푼다. `design-brief.md` §3이 이미 같은 경고를 적어놨었다. 가리거나 뒤쪽 절로 밀어도 장을 열면 드러나므로 안 쓰는 것이 유일하게 깨끗한 처리
   - **검증 부담** — 유일성 검사가 인물 1명(`verifier.ts` §1 유일성)에서 **인물 쌍**으로 올라간다. "범인 A·공범 B"와 "범인 B·공범 A"를 증거가 구분해야 하고 상호 알리바이 조합까지 배제해야 한다. 생성기가 사건마다 통과시켜야 하는 검사다
   - **핵심 규칙 이음매** — 공범은 살인엔 무고하고 L1엔 유죄라 "무고한 자는 거짓말하지 않는다"에 예외 규칙이 하나 더 붙는다. 그 도출 함수는 아직 미구현(아래 4번)이다
   - **난이도** — 예산 경고가 이미 떠 있는 상태(기대 5 + 여유 1 > 예산 5)에서 필수 조사를 더 얹을 수 없다. 기존 조사에 얹으면 공짜 답이 되어 심증 부문이 오히려 쉬워진다

   **진실 세계의 `accomplice` 역할은 남는다.** 채원이 마약망에 관여했다는 사실은 5장 동기 `폭로 임박`의 전제이고, 관계 그래프 간선은 조사로 얻은 것만 그려지므로 누설이 아니다. 공란으로 묻지만 않는다.

   부수 효과: 심증 부문이 `동기·정체·협박대상` 3라벨로 확정되어 **실제 심증 3공란과 일치한다.** "심증이 빈약하다"는 인상은 쓰지도 않을 라벨을 세고 있었기 때문이었다. 심증 확장이 정말 필요한지는 플레이테스트 "부문별 성향이 갈리는가"가 답할 질문이다.

2. **확보 단어 획득 그래프가 다름** — `engine`은 `Evidence.yieldsTerms`, `prototype`은 `TERM_MAP` 4개 + `REVEALS[s4].terms` + `SEED_TERMS` 2개. 검증기의 "`discovered` 공란 답이 실제로 획득 가능한가" 검사가 헛돌고 있다.

   3번 작업 중 발견한 부수 불일치: **물증 발견 위치가 다르다.** 엔진 `e_burner.foundAt = '별채 · 게임기 뒤'`인데 프로토타입 조사 결과 카드는 `'별채 서랍에서 발신 전용 대포폰'`이다. 오답을 유발하진 않지만 같은 물건의 서술이 갈린 것이라 2번과 함께 정리해야 한다.

   `COLLECTED_POOL`에 어떤 경로로도 확보되지 않는 항목이 셋 있다 — `수면제`·`둔기`·`유산 상속`. 후보에 뜨지 않으므로 무해하지만, 의도된 미끼였다면 획득 경로가 빠진 것이고 아니면 잔재다. 확인 필요.

3. ~~**동의어 충돌**~~ — **해소됨 (2026-07-24)**

   이름 충돌이 아니라 **한 물건이 둘로 쪼개져 있었다.** `TERM_INFO`의 `대포폰`은 "가입자 정보가 없었고, 저장된 번호는 하나뿐"(= 엔진 `e_burner`의 `record`와 동일 서술)인데, `별채 대포폰`은 "별채 안쪽에 놓여 있던 **또 다른** 선불폰"으로 적혀 있었다. 이름을 맞추려다 존재하지 않는 두 번째 폰이 생긴 것.

   엔진 기준(`e_burner.yieldsTerms = ['별채 대포폰', '김선생']`)으로 하나로 합쳤다 — `TERM_MAP['search:annex']`·`COLLECTED_POOL`·`TERM_INFO`·아이콘에서 `대포폰` 제거, `별채 대포폰`의 서술을 엔진 `record`에 맞춤. `collected` 공란 후보는 `COLLECTED_POOL.filter(w => rev[w])`이므로 이제 짧은 이름이 후보로 뜨지 않는다.

   산문·표시 라벨의 `대포폰`(조사 결과 카드, 관계 그래프 노드, 평면도 마커, `김선생` 출처 설명)은 그대로 뒀다. 후보 목록이 아니라 자연어 지칭이라 오답을 유발하지 않는다.

4. **`presence → 진술 주장 도출`이 어디에도 구현돼 있지 않음** — `SYSTEM-DECISIONS.md` §7이 "코드가 담당(전부)"에 올린 항목이고 `templates/README.md`가 "무고한 사람은 거짓말하지 않는다를 보장하는 유일한 방법"이라고 못박았는데, 검증기에 도출 함수가 없고 프로토타입은 `CLAIMS`/`CLAIM_LOC`를 손으로 쓴다. 엔진 `presence`는 무고한 4명 전원 `{t0800, main}` 한 줄뿐인 스텁이고 슬롯 어휘도 다르다(엔진 `t0300/t0330/t0400/t0500/t0800` vs 프로토타입 `t0~t3`).

| 소요 시간 미구현 | `buildResult`의 `{ k: '소요 시간', v: '—' }`. 점수 3요소(조사 횟수 + 정확도 + 시간) 중 하나 |
| 조사 예산 하드코딩 | `remaining = 5 - spent`. `Case.budget` 참조 아님 |
| 난이도 여유 0 | 기대 5 = 예산 5. 헛발질 한 번에 클리어 불가. `hard` 의도면 OK, 미결정 |
| 실존 인물명 | 예나·유진·사쿠라·유리·원영·채원. **상업 출시 전 반드시 교체** |
| 목록 모드 잔재 | 브리프 §4.1이 폐기했는데 `buildListBlank`·`buildBank`가 코드에 남아 있음 |
| 캠페인 구성 | 연작 vs 단편집. 첫 5개 집필 전 결정 필요. 현재 추천은 단편집 + 느슨한 연결 |

## 다음에 할 일 (순서가 중요)

`HANDOFF-TO-CODE.md` §0.1이 못박은 순서다. **검증되지 않은 설계를 프로덕션 스택으로 옮기면 두 번 만들게 된다.**

```
1. 문서 모순 정리 (위 표를 문서 자체에 대체 표시로 박기)
2. 엔진 ↔ 프로토타입 데이터 동기화 + 재검증
3. 플레이테스트 빌드 수리 (상황판 포함) → export
4. 플레이테스트 4명
5. 설계 보정
6. 프로덕션 구현      ← 여기가 Claude Code의 진짜 시작점
```

**4번이 가장 큰 미검증 가정이다.** 이 게임은 아직 한 번도 (앱으로) 플레이된 적이 없다. 40개 넘는 설계 결정이 미검증이고, 특히 검증기가 예측한 "조사 5회"가 실측과 맞는지 모른다. **그 숫자가 틀리면 난이도 체계 전체가 다시 계산되고 생성기 신뢰도가 무너진다.**

플레이테스트에서 측정할 것: 진행자 없이 재미있는가 / 몇 회에 풀었는가 / 부문별 성향이 갈리는가 / 순차 잠금이 답답한가 긴장인가 / 완전 침묵이 가혹한가 / **격자·상황판·관계 그래프를 실제로 쓰는가** / 어디서 지루한가 / 진술 5개가 머리에 들어오는가.

프로덕션 구현 순서는 `design-brief.md` §7 우선순위 표를 그대로 쓴다.
